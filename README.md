# order-fulfillment-guard

![test](https://github.com/qowlgur121/order-fulfillment-guard/actions/workflows/test.yml/badge.svg)

외부 공급처에서 물건을 사서 고객 주문을 처리할 때, **공급처 응답을 알 수 없는 상황에서 이중 구매를 막는 방법**을 정리한 예제입니다.

직접 운영했던 주문 자동화 시스템에서 이 부분만 떼어 내 일반화해 다시 작성했습니다. 실제 판매 채널·공급처 연동 코드와 운영 데이터는 들어 있지 않습니다. 전체 시스템 설명은 [포트폴리오](https://qowlgur121.github.io)에 있습니다.

## 문제

공급처가 5xx나 네트워크 오류를 주면 구매가 됐는지 알 수 없습니다. 보통처럼 재시도하면 이미 결제된 구매를 한 번 더 할 수 있습니다. 돈이 바로 나가는 처리라 한 번의 실수가 곧 손해입니다.

| 검토한 방법 | 문제 |
|---|---|
| 재시도 | 이미 결제됐다면 이중 구매 |
| 실패로 처리 | 이미 산 상품을 버리고 고객은 못 받음 |
| **결과 모름으로 보류한 뒤 공급처 이력과 대조 (채택)** | 처리가 몇 분 늦어짐 |

늦는 것보다 두 번 사는 쪽이 훨씬 비싸다고 판단했습니다.

## 처리 흐름

```
주문 잡기 → 안전장치(비상 정지 · 하루 상한) → 구매 시도 기록(POSTING) → 공급처 구매
  ├─ 성공       → CONFIRMED → 주문 BOUGHT
  ├─ 명확한 거절 → REJECTED  → 30초 ~ 15분 지수 백오프 후 재시도
  └─ 결과 모름   → AMBIGUOUS → 재구매 금지, 공급처 이력과 대조
                    ├─ 정확히 1건 일치 → CONFIRMED로 복구
                    ├─ 0건 → 다시 대조 (공급처 반영이 늦을 수 있음), 유예 시간 뒤에도 0건이면 사람 검토
                    └─ 여러 건 → 어느 것이 이 주문인지 모름 → 사람 검토
```

- **중복은 DB가 막습니다.** 주문번호가 PRIMARY KEY라 같은 주문은 한 줄뿐이고, 상태 변경은 `WHERE status=?` 조건부 UPDATE라 워커가 둘이어도 한 명만 주문을 잡습니다.
- **공급처를 부르기 전에 "지금 산다"를 먼저 기록합니다.** 호출 중 프로세스가 죽어 `POSTING`이 남아 있으면 결과 모름과 같이 취급해 재구매하지 않습니다.
- **모르면 추측하지 않습니다.** 이력 조회까지 실패하면 판단을 미루고, 후보가 여러 건이면 사람에게 넘깁니다.

## 재현 테스트

운영하며 신경 썼던 상황을 테스트로 고정했습니다. 고친 코드가 다시 깨지면 배포 전에 걸립니다.

| 상황 | 기대 |
|---|---|
| 결과 모름 + 실제로는 결제됨 | 재구매 없이 이력에서 복구 |
| 결과 모름 + 공급처 반영이 늦음 | 다음 대조에서 복구, 그 사이 재구매 없음 |
| 결과 모름 + 유예 시간 뒤에도 0건 | 사람 검토 + 알림 |
| 같은 상품 · 수량의 이력 후보가 여러 건 | 사람 검토 |
| 이력 조회 실패 | 판단 보류 |
| 요청 중 프로세스 종료 (`POSTING` 잔존) | 결과 모름으로 처리 |
| 구매 확정 직후 프로세스 종료 | 재구매 없이 진행 |
| 워커 2개가 같은 주문을 동시에 잡음 | 한 명만 성공 |
| 비상 정지 · 하루 상한 도달 | 구매 API 호출 없음 |

```bash
pip install pytest
pytest -q
```

## 구성

```
fulfillment/
  store.py     SQLite 스키마, 조건부 상태 전이
  supplier.py  공급처 경계: 성공 / Rejected / Ambiguous
  worker.py    주문 한 건 처리 흐름과 대조 로직
tests/
  test_worker.py
```

표준 라이브러리만 씁니다 (Python 3.10+, 테스트는 pytest).

## 운영 규모에서 바꿀 부분

이 예제는 서버 1대 · SQLite 기준입니다. 주문이 열 배가 되면 PostgreSQL로 옮기고, 주문 처리를 작업 큐와 워커로 나눠 `SELECT … FOR UPDATE SKIP LOCKED`로 주문을 잡게 바꿀 계획이었습니다.
